# Audit — 6 November 2026

## Follow-up: 2.1.5

A real user report after 2.1.4 exposed a failure not covered by the original short
capture smoke tests. A longer 60 FPS AV1 run reproduced the watchdog stopping a
buffer that was falling behind real time. Silent PCM packet delivery accumulated
timer delay; older session logs also showed Windows manifest-rename conflicts.
The audio writer now uses absolute monotonic deadlines and the manifest is
append-only, read through bounded snapshots. Startup logging is forced on so
preexisting dependency handlers cannot silently disable the file log.

113 tests passed. A 90-second regression capture maintained advancing segments,
made three replay exports during recording, and fully decoded all three. Longer
hardware/session testing remains necessary. The original 2.1.4 results below
describe the checks actually performed at that time, not proof against this bug.

FFmpeg with DXGI capture and hardware encoding remains a reasonable base. The
confirmed failure was in replay lifecycle handling, rather than the codec.
The application still needs broader capture and detection validation before it
can promise reliable unattended highlights across games and computers.

## Recorded-session checks

- 20 existing recordings, 459.51 seconds and 1.44 GB in total.
- Every file decoded fully, including all audio streams, without decoder errors.
- All were AV1, 2560 × 1440, 60 FPS, with mix, microphone and chat tracks.
- Frame-by-frame decoding, 4 Hz HUD analysis and selected visual spot checks were
  used. This was not a manual review of every frame or conversation.
- HUD analysis found 19 kill indications and one assist across 18 automatic clips.
- One other automatic clip had a marker at 26.25 seconds in a 20-second file;
  the saved picture did not confirm that marked elimination.
- The remaining file was a manual replay without a detected HUD action.

Only saved clips were available. These checks cannot measure missed events in
the unsaved parts of the full gaming session. Container FPS does not measure
game FPS, capture latency or the number of distinct captured frames.

## Changes in 2.1.4

| Finding | Change |
| --- | --- |
| New detections could use retained footage while capture was stopped after switching windows. Pending events could then delay capture restarting. | Automatic events require an active, ready capture. |
| Stopping capture during post-roll shifted the requested range backwards and could write markers beyond the saved picture. | Keep the requested start, separate missing markers, report partial replays, and refuse unrelated footage outside the buffer. |
| A stopped encoder could leave a plausible-looking, stale buffer. | Detect 12 seconds without new completed segments and report a capture error. Restart recording to recover. |
| Old invalid markers disappeared silently from editing. | Show source-integrity warnings in the plan and export report. |
| Recorded-match analysis repeatedly sought through AV1 on CPU. OCR variations could count a persistent row repeatedly. | Prefer the shared calibrated pixel detector for the matching player. OCR fallback uses a sequential GPU/CPU decode pass; its results still require review. |
| Additional chat recording was tied to Sonar. | Choose an ordinary WASAPI playback output in Settings or first-run setup. Keep automatic Sonar support and avoid recording the exact same endpoint twice. |
| Completion/error dialogs from background editing could activate the app during gameplay. | Keep the result/status in the app and suppress those modal dialogs while the game is foreground. This does not establish the cause of the earlier clip-save report. |
| Historical validation notes described an unpublished repository and outdated UI. | Replace them with this current report. |

The stale-buffer condition is reproduced by a regression test and is consistent
with the invalid saved marker. There is no historical foreground-window trace
proving the exact sequence for that particular clip.

The calibrated scanner found the two expected actions in each of two recordings
in 6.0 and 4.6 seconds locally. A sequential OCR trial took about 32 seconds per
clip and returned extra/duplicate detections. These are local samples, not a
general speed or accuracy guarantee. A separate old random-seek trial was stopped
before completion and is not used for a numerical speed comparison.

## Remaining work, in priority order

| Priority | Work | Reason |
| --- | --- | --- |
| High | Track row identities and verify repeated/full killfeeds. | The live pixel matcher currently triggers when the number of matching player-name rows increases. Replacing one row while the count stays equal can be missed. A pixel template is not semantic understanding of every kill. |
| High | Offer optional full-session recording and an event review timeline. | A replay buffer deletes old material. It cannot recover missed events after they leave the buffer. |
| High | Add capture of the selected game window, plus privacy tests around Alt+Tab. | Current capture records the entire selected monitor. Foreground polling and the UI tick can take about 1.5 seconds to stop it after leaving the game. |
| High | Add multiple-adapter output enumeration and laptop/hybrid-GPU tests. | Current monitor enumeration uses DXGI adapter 0. Presets alone do not validate other GPU/display wiring. |
| Medium | Supply and validate assist profiles for other HUD languages/layouts. | The bundled assist notification template is Polish. English application UI does not change the game's HUD language support. |
| Medium | Add disk budget, low-space warnings and safe crash-buffer recovery. | Long/high-bitrate buffers consume gigabytes; interrupted sessions can leave temporary data. |
| Medium | Test latency, frame pacing, audio sync, long sessions and driver changes on physical AMD/Intel/older NVIDIA hardware. | A successful codec smoke test does not establish smooth gameplay performance. |
| Medium | Add a manual timeline with per-event trim and preview before export. | Automatic context windows cannot judge every joke, reaction or cinematic cut. |
| Medium | Sign the installer and automate release checks. | The installer remains unsigned; local validation is not a broad release test matrix. |
| Low | Add hot-plug refresh for audio outputs and persist native endpoint identifiers. | Selected output names survive index changes, but renaming or disconnecting a device still requires selecting it again. |

The earlier focus-loss report was not reproduced in passive observation of a
manual and an automatic save. No focus fix is claimed. A deliberately opened QA
setup preview activated its window; that is separate from automatic saving.

## Engine direction

Keep hardware encoding and the media tools. Add a Windows Graphics Capture backend
for individual windows rather than rewriting editing and encoding together.
Windows Graphics Capture supports display/window capture; HDR needs an explicit
floating-point capture pipeline to avoid washed-out output. Current recordings
are tagged SDR BT.709, not a validated HDR workflow.
[Microsoft capture documentation](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)
and [Desktop Duplication documentation](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api).

GPU decoding does not imply every operation runs on the GPU: OCR, audio analysis,
some filters and control logic still use the CPU. Hardware download transfers
frames back to system memory.
[FFmpeg filter documentation](https://ffmpeg.org/ffmpeg-filters.html).

Support remains **War Dogs**. Private recordings, player profiles and detailed
per-file evidence are kept outside the public repository.

## Release validation

110 tests passed, together with a packaged-runtime self-test and a privacy audit
of 29 application modules. Real DXGI recording with an explicitly selected headset
output passed with microphone recording on and off; both exports decoded fully.
The existing recordings had measurable microphone signal in all 20 files and chat
signal above -70 dBFS peak in 17. Quiet tracks do not establish that speech was lost.

A kills-and-assists plan for all recordings contains 18 shots, about 134.55 seconds,
and an explicit warning for the invalid source. A separate two-source export was
20.17 seconds long, took 17.08 seconds locally, and decoded fully. The plan reused
the verified event scan; the source recordings were not modified.
